调度设计说明

一、补充目的

原项目已经具备统一执行入口、批量运行脚本、ETL 日志表和数据质量校验脚本，但整体仍以脚本顺序执行为主。为了进一步贴近离线数仓项目的工程化场景，在现有项目基础上补充梳理任务依赖、批次管理、失败重跑和结果验收等调度设计思路，用于理解离线任务从“顺序执行脚本”向“可编排批处理流程”扩展的基本方式。

二、任务链路设计

本项目按离线数仓处理顺序划分为以下任务阶段：

1. DWD 清洗任务  
对原始订单数据进行清洗，过滤异常数量、异常价格、空客户和退货订单，生成清洗后的明细表。

2. DWS 汇总任务  
基于清洗后的明细表，生成销售汇总表和客户价值分层表。

3. ADS 指标任务  
基于 DWS 汇总结果继续生成复购率、月度趋势、国家价值分析、客户分层分布、高价值客户销售贡献等应用层指标表。

4. 数据质量校验任务  
对关键结果表进行校验，检查数据是否为空、结果表是否成功生成，以及关键字段是否存在异常值。

三、任务依赖关系

任务依赖关系按数仓分层顺序执行：
DWD -> DWS -> ADS -> 数据质量校验

即：
- DWD 成功后才能运行 DWS
- DWS 成功后才能运行 ADS
- ADS 成功后才能执行结果校验
- 若前序任务失败，则后续任务不继续执行

四、批次管理设计

为了便于查看每次 ETL 任务的执行情况，项目中通过 `etl_task_log` 表记录任务运行日志，并为每次运行设置批次号 `batch_id`。每个批次可记录任务开始、成功或失败状态，便于后续追踪某次离线运行的完整过程。

五、失败处理思路

当某一层任务执行失败时，应停止后续任务执行，优先排查失败原因。问题修复后，可基于同一批次或新批次重新执行失败任务及其后续任务。该设计有助于避免下游结果基于错误或不完整数据生成。

六、结果验收设计

每次批处理完成后，使用数据质量校验脚本对核心结果表进行检查，包括：
1. 清洗表中是否仍存在异常数量、异常价格、空客户和退货订单；
2. DWS 客户分层结果是否为空；
3. ADS 关键指标表是否成功生成；
4. Top10、趋势表、高价值客户相关结果表是否满足预期行数或非空要求。

七、当前理解

通过本次补充，进一步理解了离线数仓项目不仅要“计算结果”，还要关注“如何按顺序执行、如何记录执行过程、失败后如何处理、结果如何验收”。当前项目虽未接入正式调度平台，但已具备从统一 SQL 执行向调度编排思路扩展的基础。

八、可对外描述的项目补充

在现有 MySQL 电商离线数仓项目基础上，进一步梳理了离线任务链路与调度设计思路，围绕 DWD 清洗、DWS 汇总、ADS 指标落表和数据质量校验四个阶段，补充了任务依赖关系、批次管理、失败重跑和结果验收流程，对离线数仓项目从顺序执行脚本向可编排批处理流程扩展形成了初步实践认识。
